# 后端能力真实化开发计划

> 状态：草案 v0.1 — 2026-07
> 目标：将前端从「全本地 mock 驱动」逐步切换为调用真实 BFF（Spring Boot BFF → Dify）接口，对齐 `docs/后端架构方案.md` 的接口契约。
> 配套文档：`docs/后端架构方案.md`（后端契约）、`docs/前端差距清单.md`（待补功能清单）。

---

## 0. 目标与范围

**目标**

将前端业务模块从「本地 mock + setTimeout 模拟」逐步替换为真实后端接口调用，做到：

- 每个模块可独立、可灰度地在「mock / 真实」之间切换，默认可回退；
- 接口契约对齐 `docs/后端架构方案.md`；
- 长任务（渡河 / 规划 1h 场景）走 WebSocket 流式 + checkpoint 续跑；
- 不破坏现有 UI 形态与视觉风格。

**范围**

| 模块                                             | 是否本期 | 说明                                                          |
| ------------------------------------------------ | -------- | ------------------------------------------------------------- |
| `catalog`（数据目录）                            | ✅       | 只读列表 / 筛选，低风险先行                                   |
| `knowledge`（地理知识库）                        | ✅       | 混合检索（BM25+向量+图谱+Rerank）                             |
| `agent`（智能体工作台）                          | ✅       | 会话 + 流式 + 工具调用链 + WS                                 |
| `river`（渡河保障）                              | ✅       | 长任务，9 步流水线对接真实 workflow                           |
| `planning`（机动规划）                           | ✅       | 长任务，路线方案对接真实                                      |
| `screen`（统计大屏）                             | ✅       | 聚合统计端点 + 实时刷新                                       |
| 系统模块（auth/route/online/log/monitor）        | ❌       | 已接真实 `realRequest`，不在范围                              |
| `building`（楼宇夺控）                           | ❌       | 前端页面已移除；`building-control` 智能体契约保留，暂不接前端 |
| Web 球 / 数据接入（影像·DEM·瓦片·矢量·对象存储） | ❌       | 后端架构方案已声明「不讨论」                                  |

## 1. 现状盘点（As-Is）

### 1.1 业务数据如何被消费（问题根因）

业务功能全部在各自的 composable / mock 模块中**直接 import 本地数据**，不存在 HTTP 调用：

- `src/mock/catalog.ts`、`knowledge.ts`、`agent.ts`、`river.ts`、`planning.ts`、`screen.ts` 被 34 个视图/composable 直接 import；
- 异步靠 `sleep()`、`runKnowledgeRetrieval()` 等模拟，UI 加载态与真实网络无关；
- 数据形态为「前端预设假数据」，与后端契约（`docs/后端架构方案.md` §5.3 / §6.3）无对齐。

### 1.2 已具备的真实能力（可复用）

- `src/service/request/real.ts`：已封装 `realRequest`（基于 axios，baseURL = `VITE_SERVICE_REAL_BASE_URL` = `http://localhost:8000`，含 Bearer token、成功码 `0000`、登出码、token 过期刷新）；
- `src/service/api/{auth,route,system,monitor}.ts`：已用 `realRequest` 对接真实后端，证明链路（请求层→类型→错误处理）可用；
- 运行时配置：`public/config.json` → `window.__APP_CONFIG__`，构建后可直接覆盖（见 `src/utils/service.ts`），无需重构建——**这是做灰度开关的最佳载体**。

### 1.3 当前缺口

| 缺口                                  | 影响                           |
| ------------------------------------- | ------------------------------ |
| 业务 composable 未走 `service/api` 层 | 无真实接口入口                 |
| 无 WebSocket / SSE 客户端             | Agent 流式、长任务进度无法对接 |
| 无逐功能 mock/real 开关               | 无法灰度、无法安全回退         |
| 前端类型未对齐 BFF 契约               | 接真实接口时类型漂移、编译失败 |
| 错误归一 / 重连 / checkpoint 机制缺失 | 长任务 1h 场景不可靠           |

### 1.4 数据分级（决定哪些要迁、哪些保留）

`src/mock/*` 内容分两类，迁移时只迁「业务数据」，保留「纯前端展示配置」：

- **业务数据（需迁）**：catalog 文档/场景列表、knowledge 检索结果、agent 列表与产物、river 方案结果、planning 路线、screen 统计 KPI。
- **纯展示配置（保留）**：`riverDefaultLayers`、`riverFlowTemplate`、`riverPresets` 等 UI 静态模板（非后端下发，属前端编排配置）。

## 2. 总体策略：数据源抽象 + 渐进切换

采用「**composable 依赖 service 接口，service 内部按开关选择 mock/real 实现**」的低风险模式，保证每迁一个模块、可验证一个、可回退一个。

### 2.1 统一开关（复用运行时配置）

扩展 `public/config.json`（即 `window.__APP_CONFIG__`）增加逐功能开关：

```jsonc
{
  // ...既有字段...
  "FEATURE_API_REAL": {
    "catalog": false,
    "knowledge": false,
    "agent": false,
    "river": false,
    "planning": false,
    "screen": false
  }
}
```

新增 `src/service/switch.ts`：

```ts
export function isRealApi(feature: keyof App.Service.FeatureApiReal): boolean {
  const cfg = (window as any).__APP_CONFIG__;
  return Boolean(cfg?.FEATURE_API_REAL?.[feature]);
}
```

> 部署后改 `public/config.json` 即可逐功能开/关真实接口，无需重新构建。

### 2.2 每功能一套 service 层（真实实现）

新增 `src/service/api/<feature>.ts`，函数签名与 composable 当前调用 1:1 对齐，内部用 `realRequest`，返回 `Promise<T>`：

- `catalog.ts`：`getCatalogList(params)`、`getScenarioTags()` …
- `knowledge.ts`：`searchKnowledge(query, opts)`、`getDocuments()` …
- `agent.ts`：`listAgents()`、`createSession()`、`sendMessage()`（流式/WS）、`cancel()`、`fork()`、`getArtifacts()`
- `river.ts` / `planning.ts`：`createTaskSession()`、订阅进度、取产物
- `screen.ts`：`getScreenStats()`、`subscribeScreen()`

### 2.3 复用现有 mock 作为兜底实现

将 `src/mock/*` 中「业务数据」函数重包为 async（加 `sleep` 模拟延迟），作为 `isRealApi` 为 `false` 时的默认实现。composable 改为：

```ts
// 旧：import { catalogList } from '@/mock/catalog';
// 新：
import { getCatalogList } from '@/service/api/catalog';
const list = await getCatalogList(params);
```

service 内部：

```ts
export async function getCatalogList(params: CatalogQuery) {
  if (isRealApi('catalog')) {
    return realRequest.get<Api.CatalogListResp>('/api/kb/documents', { params });
  }
  return mockGetCatalogList(params); // 既有逻辑包成 async
}
```

### 2.4 WebSocket 客户端（长任务 / 流式）

新增 `src/service/request/ws.ts`：封装原生 WebSocket 连接 `/ws/agent/sessions/{id}`，提供：

- 连接 / 断线自动重连（指数退避 + 心跳）；
- 事件分发（message / tool_call / task_complete / artifact）；
- 断线补偿：`GET /api/agent/sessions/{id}?fromMessageId=` 全量补偿（对齐后端架构方案 §6.4）。

## 3. 分阶段路线

对齐 `docs/后端架构方案.md` §14 里程碑（W1–W4），前端配合推进。

### Phase 0 — 基础设施（前置，约 1.5d）

- [ ] 扩展 `public/config.json` 增加 `FEATURE_API_REAL` 开关 + `src/service/switch.ts`
- [ ] 新增 `src/service/request/ws.ts`（WS 封装 + 重连 + 事件分发）
- [ ] 定义与后端对齐的共享类型 `src/service/types`（参照 §5.3 / §6.3）：`KbDocument`、`KbSearchResult`、`AgentSession`、`AgentMessage`、`AgentArtifact`、`TaskProgress` 等
- [ ] 建立 `src/service/api/<feature>.ts` 骨架 + mock 兜底模板
- [ ] 错误归一封装：`DIFY_UPSTREAM_ERROR` 等 → 统一 toast（复用 `realRequest` 的响应拦截）
- [ ] 与后端确认接口契约（OpenAPI/JSON Schema），前端落 `src/service/types`

### Phase 1 — 低风险只读接口：`catalog` + `knowledge`（约 2d）

- [ ] `catalog`：`GET /api/kb/documents?type=` 替换本地列表与场景筛选；保留本地为 mock 兜底
- [ ] `knowledge`：`GET /api/kb/documents` + `POST /api/kb/search` 替换 `runKnowledgeRetrieval`；混合检索结果（bm25/vector/graph + rerank 加权）直接驱动命中高亮与相似度分
- [ ] 打通「真实请求 → 类型对齐 → loading/错误态 → 回退 mock」闭环
- [ ] 验收：本地起 BFF + Dify + Ollama 后，`catalog`/`knowledge` 开关置 `true` 端到端跑通

### Phase 2 — Agent 会话与流式：`agent` 模块（约 3d，最关键）

- [ ] `GET /api/agent/agents` 替换 `getAgentByKey` 静态表（agents 由后端产出）
- [ ] `POST /api/agent/sessions` + `messages`（SSE/WS）替换本地对话模拟
- [ ] 工具调用链可视化对接真实 `tool_calls` 事件（LLM→工具→结果 三段式 + 耗时）
- [ ] `cancel` / `fork` 对接真实端点
- [ ] 模型绑定状态指示对接后端 agent 元数据
- [ ] 长任务 `task_complete` 事件驱动跳结果页

### Phase 3 — 长任务业务流：`river` + `planning`（约 3d）

- [ ] `river-crossing`：`POST /api/agent/sessions {agentKey:'river-crossing'}`，9 步流水线进度对接真实 WS 事件流（替换 `sleep` 模拟）
- [ ] 多方案对比、规则验证面板对接真实 `artifacts`
- [ ] `planning`：`POST /api/agent/sessions {agentKey:'planning'}`，机动路线规划对接真实
- [ ] checkpoint 续跑：重连后 `GET /sessions/{id}?fromMessageId=` 补进度（对齐 §6.4）
- [ ] 耗时计时器对接真实任务起止时间

### Phase 4 — 大屏聚合：`screen`（约 1.5d）

- [ ] `screen` 混用 mock 改为 `GET /api/agent/sessions?status=completed` 等聚合端点
- [ ] 新增 4 个 KPI（模型准确率 / 方案耗时 / 规则命中率 / 障碍物识别率）+ 校验通过率雷达轴，对接真实统计端点
- [ ] 实时刷新走 WS（或轮询兜底）

### Phase 5 — 收尾与去 mock（约 1.5d）

- [ ] 各模块 `FEATURE_API_REAL` 默认置 `true`
- [ ] 清理 `src/mock/*` 中已迁出的「业务数据」；保留纯前端展示配置（`riverDefaultLayers` 等）
- [ ] 错误归一、重连、监控埋点补齐
- [ ] 补充集成测试 / E2E（mock 与 real 双路）

**总计约 12.5 人日 ≈ 2.5 周（单前端，依赖后端 BFF 同期就绪）**

## 4. 关键技术点

| 主题     | 方案                                                                                        |
| -------- | ------------------------------------------------------------------------------------------- |
| 类型契约 | 前端 `src/service/types` ↔ 后端架构方案 §5.3/§6.3；用 OpenAPI/JSON Schema 约定，CI 校验漂移 |
| 流式选择 | 后端给 WS，前端用 `src/service/request/ws.ts` 原生 WS 封装；SSE 作备选                      |
| 鉴权透传 | `realRequest` 已带 Bearer；确认 OIDC context 注入字段（角色/选中目录/视图范围）             |
| 断线重连 | 指数退避 + 心跳；`GET /sessions/{id}?fromMessageId=` 补偿                                   |
| 加载态   | 骨架屏 + 流式增量渲染（本地 Ollama ~3–5 token/s，不可阻塞 UI）                              |
| 灰度     | `FEATURE_API_REAL` 逐功能开关，默认可回退到 mock                                            |
| 错误归一 | `DIFY_UPSTREAM_ERROR` 等 → 统一 toast，不暴露后端细节                                       |

## 5. 风险与回退

| 风险                 | 概率 | 影响 | 缓解                             | 回退                 |
| -------------------- | ---- | ---- | -------------------------------- | -------------------- |
| 后端 BFF 未就绪      | 高   | 高   | 开关默认 `false`，保留 mock 兜底 | 不动开关，纯前端可跑 |
| 长任务 1h 断线       | 高   | 中   | WS 重连 + `fromMessageId` 补偿   | 改同步轮询           |
| 前后端类型漂移       | 中   | 中   | 接口契约文件 + CI 校验           | 临时 `any` + 告警    |
| 本地 Ollama 慢       | 中   | 低   | 增量渲染 + 骨架屏                | 降低默认 topK        |
| 切真实后 UI 形态变化 | 中   | 低   | Phase 内先验证再开默认           | 关回 mock            |

---

## 6. 验收标准

每个模块迁移完成时，需同时满足：

1. `FEATURE_API_REAL.<feature>=true` 时，交互全部走真实接口；`=false` 时回退本地 mock；
2. 类型检查（`pnpm typecheck`）+ lint（`pnpm lint`）通过；
3. 加载态 / 错误态 / 重连态有可见反馈；
4. 至少 `catalog` + `knowledge` 在 Phase 1 端到端跑通（依赖本地 BFF + Dify + Ollama 起得来）；
5. 视觉风格（深色玻璃态 + 蓝青配色）与现有 8 模块一致。
