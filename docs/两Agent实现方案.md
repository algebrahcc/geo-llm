# 两 Agent 可落地实现方案

> 目标：基于 Dify 实现 **渡河保障助手** 与 **路线规划助手** 两个 agent，逐项对齐 `D:\WorkSpace\chikawa\指标.md`（指标1）与 `指标2.md`（指标2）。
> 原则：**LLM 只做"理解、抽取、生成、编排"，硬指标（图像识别、地理计算、规则校验、瓦片服务、路径规划）全部下沉到外部工具/服务**，Dify 通过工具节点 + code 节点调用。

---

## 0. 总体架构与分工

```
┌─────────────────────────────────────────────────────────────┐
│                         前端 (现有高保真原型)                   │
│   river/planning 模块 · 展示 agent 输入输出 · 人工校验界面        │
└──────────────────────────────┬──────────────────────────────┘
                               │ HTTP / WebSocket
┌──────────────────────────────▼──────────────────────────────┐
│                       Dify (编排中枢)                         │
│  Workflow · LLM 节点 · 知识检索 · 工具节点 · Code 节点           │
│  渡河保障助手 / 路线规划助手 · Human Input 节点(HITL)            │
└──────┬────────────────┬────────────────┬─────────────────────┘
       │                │                │
       ▼                ▼                ▼
  工具服务(Java主力)   Python增强服务    基础服务
  (Spring Boot)     (有优势再独立)   (PostGIS/MinIO/向量库)
   · 规则引擎          · 图像识别(可选)    · 渡河知识库(RAG)
   · 地理编码          · 视觉模型推理      · 地理环境基础库
   · 路网/路径规划      · 栅格/向量计算     · 瓦片服务 TMS/WMS/WMTS
   · 跨模态融合        · 深度学习微调
```

**两个 agent 的能力边界：**

| Agent | 对应指标 | 定位 |
|-------|---------|------|
| 渡河保障助手 | 指标1 全文 | 接收指令/情报/现场图片 → 解析意图、抽取参数 → 融合知识库与图像要素 → 生成渡河保障方案（含多方案、规则校验、人工校验） |
| 路线规划助手 | 指标2：A-7/A-8、C 标绘、D 障碍物、第四系统（路网/机动路线规划） | 接收自然语言路线需求/影像 → 解析到坐标与约束 → 叠障碍物与地形 → 输出机动路线、评估报告、多场景对比 |

**统一约定（两个 agent 共用）：**
- 所有外部能力封装为 Dify **工具**（接入方式见 §0.2）。
- 所有 LLM 输出用 **JSON Schema 结构化输出**，禁止自由文本。
- 所有"有把握但需确认"的结果走 **人工确认节点**，人工修正数据回流落库。
- 每个 agent 配一个 **评测集 + 评测脚本**，形成可度量的指标回路。

### 0.1 Dify 1.16.0 应用类型选择（基于新版能力）

Dify 1.16 提供：**Agent（新版 Dify Agent，Beta，Linux 沙箱 + Skills 文件体系）、聊天助手 (Chatbot)、工作流 (Workflow)、对话流 (Chatflow)、文本生成**。本方案**以 Workflow 为主编排、内嵌 Agent 节点**（不依赖 Chatflow）：

| 类型 | 特点 | 结论 |
|------|------|------|
| 聊天助手 (Chatbot) | 直接对话 + Agent 模式，无显式流程节点 | 不用 |
| **Agent（新版 Dify Agent）** | **Linux 沙箱运行 + Skills + 工具自主编排，可在 Workflow 中作为节点调用** | ✅ 用于"需要自主推理/多工具协作"的子任务 |
| 工作流 (Workflow) | **User Input 开始 → LLM/知识检索/工具/Code/If-Else/Iteration/Human Input/Parameter Extractor/Question Classifier/Agent 节点，Output 结束** | ✅ **两个 agent 的主编排框架** |
| 对话流 (Chatflow) | 带对话层的工作流 | 可用可不用；本方案不依赖它 |
| 文本生成 | 单轮文本生成 | 不用 |

选择依据（与 1.16 能力一一对应）：
1. 指标要求的是**确定性多步流程**（解析→抽取→检索→识别→融合→筛选→生成→规则校验→人工确认）——**Workflow 的节点画布完全承载**，可评测、可回溯、可版本控制。
2. 需要**人工校验/修正**（指标1 人工校验 ≥75%、指标2 标注回流）——Workflow 内置 **Human Input（人工输入）节点**，流程暂停等人确认，API 提供 Get/Submit Human Input Form。
3. 需要**结构化抽取**——Workflow 内置 **Parameter Extractor 节点**（JSON Schema 输出）与 **Question Classifier 节点**（意图/多分类），直接对指标1的"数十项参数抽取 + 意图多分类"。
4. 需要"自主决定调哪个工具"的环节——**新版 Dify Agent（Beta，沙箱+Skills）**在 Workflow 中以 **Agent 节点**嵌入（可选官方推理策略），局部自主、整体可控；复杂计算走沙箱/外部工具。

> 官方文档中 Chatflow 仍存在，但 1.16 已将 Agent 提升为一等公民；本方案刻意只依赖 **Workflow + Agent 节点 + 外部工具**，你在界面上不依赖 Chatflow 也能完整落地。

### 0.2 "工具"是什么（含是否 MCP）

Dify 中"工具"= 供 LLM/工作流调用的外部能力单元，来源有三类：

| 来源 | 说明 |
|------|------|
| 内置工具 | Dify 自带（网页搜索、Wikipedia 等） |
| **自定义 HTTP 工具** | 自建后端 API → 导入 OpenAPI/Swagger 即变工具 |
| **MCP 工具** | 服务包装为 MCP Server，Dify 作 MCP 客户端接入（1.16 已支持 MCP 2025-06-18 协议 + 版本协商 + 结构化工具输出 + 动态请求头注入） |

本方案的工具 = 自建 **Spring Boot (Java) 工具服务**（规则引擎、地理编码、路径规划、渡厂筛选、跨模态融合等；图像识别、视觉模型推理按需单独 Python 服务），接入 Dify 两种方式：

- **方式 A（先做）**：Spring Boot 使用 `springdoc-openapi` 自动生成 OpenAPI/Swagger → Dify「工具 → 自定义工具 → 导入 OpenAPI」→ 每个 API 变一个工具，最快打通。
- **方式 B（推荐，1.16 原生利好）**：将工具服务包装为 **MCP Server** → Dify 添加 MCP 服务器 → 工具自动出现；1.16 支持结构化工具输出与运行时动态请求头（便于逐请求鉴权透传），更标准化、利于对接第三方 GIS/模型服务。

> 技术栈约定：**工具服务默认 Spring Boot (Java) 开发**；只有当某项能力在 Python 生态有明显优势（如 PyTorch/OpenCV 视觉模型、GDAL/rasterio 栅格计算、numpy 矩阵运算）时，才拆分独立 Python 微服务，通过 HTTP/内部 API 供 Java 侧调用。

> 注：方案中 "code 节点" 指 Workflow 内嵌的 Python/JS 脚本节点（如规则计算、向量拼接），不是工具。

## 1. Agent A：渡河保障助手（对应指标1）

### 1.1 输入 / 输出定义

| 项 | 内容 |
|----|------|
| 输入 | ① 作战指令/情报报告文本 ② 无人机/无人艇回传现场图片（可选） ③ 人工补充参数（可选） |
| 输出 | 结构化 JSON：意图、抽取参数表、候选渡厂评分、渡河保障方案（渡口选址/浮桥构筑/交通管制/工程保障）、规则校验结果、多方案对比、置信度与待确认项 |

### 1.2 Dify 工作流（Workflow + Agent 节点）编排序列

```
[开始-User Input] 接收: 指令文本 + 现场图片(可选)
   │
   ├─[Question Classifier] 意图识别与多分类
   │        → {primaryIntent: 快速渡河|隐蔽渡河|..., tasks: [渡口选址|浮桥构筑|交通管制|...]}
   │
   ├─[Code] 文本清洗/预处理 (去空白、统一全半角、敏感词脱敏、长度截断)
   │
   ├─[知识检索] 渡河保障知识库 RAG (知识增强检索)
   │        → top-k 相关条目
   │
   ├─[Parameter Extractor] 参数抽取 (JSON Schema 约束, 数十项: 水温/水深/流速/岸滩坡度/地质/d情威胁/路网...)
   │        → 字段带来源标记 {text|image|unknown} 与置信度
   │
   ├─[工具] 图像水域要素识别API (流速/水深/岸滩坡度)   ← 当输入含图片时
   │        → 图像识别要素 + 置信度
   │
   ├─[Code] 跨模态融合: 文本向量 + 图像特征向量 → 加权融合向量
   │
   ├─[工具] 渡厂智能筛选API (候选生成 + 适宜性多因子评分)
   │        → 候选渡厂列表 + 评分
   │
   ├─[LLM] 渡河保障方案生成 (基于融合结果 + 候选渡厂 + 知识库)
   │        → 渡口选址/浮桥构筑/交通管制/工程保障 4 类方案草稿
   │
   ├─[工具] 规则引擎校验API (浮桥跨度↔水深、流速阈值、坡度阈值等硬约束)
   │        → {pass/fail, 失败项, 建议调整}
   │        ├─ 不通过 → [If-Else] 回 [LLM 方案生成] 重新生成 (附失败原因, 最多 2 次重试)
   │        └─ 通过 ─┐
   ├─[LLM] 多方案对比与推荐 (2~3 套方案 + 推荐理由 + 权衡项)
   ├─[Human Input] 人工确认节点 展示待确认项 (低置信参数/方案选择)
   │        ├─ 确认/修正 → 修正数据回流 API
   │        └─ 直接通过
   └─[Output] 输出完整 JSON 方案 → 前端 river 模块渲染
```

### 1.3 外部工具清单（Spring Boot 工具服务实现）

| 工具 | API | 输入 | 输出 | 指标对应 | 实现 |
|------|-----|------|------|---------|------|
| 图像水域要素识别 | `POST /tools/image/water-features` | 图片文件 | 流速、水深、岸滩坡度、水体特征 + 置信度 | 指标1 K-7 | 可 Java（OpenCV+回归）或 Python（深度模型） |
| 渡厂智能筛选 | `POST /tools/ford/screen` | 河段信息+参数表 | 候选渡厂、适宜性评分、推荐解释 | 指标1 核心 | Java |
| 规则引擎校验 | `POST /tools/rule/validate` | 方案 JSON | pass/fail + 失败项 + 建议 | 指标1 K-5 | Java（Drools/Easy Rules） |
| 跨模态融合 | `POST /tools/fusion/vectorize` | 文本+图像 | 融合向量（供 LLM 注入） | 指标1 K-8 | Java（向量拼接/加权） |
| 参数修正回流 | `POST /tools/feedback/correct` | 参数名+修正值 | 落库确认 | 指标1 人工校验 | Java |

### 1.4 关键实现细节

**参数抽取（对齐 K-3，准确率≥75%）**
- 用 JSON Schema 定义数十项参数 schema（`temperature_water`, `depth_min`, `flow_speed`, `bank_slope`, `geology`, `threat_intensity`, ...），字段含 `value/unit/source/confidence`。
- 每个字段用 `{source: text|image|default|unknown, confidence}` 标记来源，`unknown` 项进入人工确认节点。
- **评测回路**：建 100 条真实指令+标注答案的评测集 → 离线跑 `抽取准确率 = 全字段完全匹配的样本数 / 总样本数`，低于 75% 则补语料/调提示词/加 few-shot，直到达标。

**规则引擎（对齐 K-5）**
- 规则写成声明式 JSON（Java Drools/Easy Rules 或自研），示例：
  ```json
  { "rule": "浮桥跨度与水深匹配",
    "condition": "floatBridgeSpan >= depth_max * 8",
    "onFail": "浮桥跨度不足，建议增加至 XX 米" }
  ```
- 校验不通过时，把失败原因拼进重新生成的 prompt，实现"生成→校验→再生成"闭环。

**时效 ≤1 小时（对齐指标 K-9）**
- LLM 链路本身秒级；耗时可控点放在图像识别、切片发布等重活 → 用异步任务 + 状态查询，前端先给"分析中…"进度。

**RAG 知识库（对齐 K-1）**
- 把 `src/mock/knowledge.ts` 的条目整理为真实知识条目（渡河规程、水文参数表、装备参数、案例），Dify 知识库 + embedding（bge-m3 或 bce-embedding）+ 向量库。

### 1.5 提示词框架（骨架）

```
【系统】你是渡河工程保障专家助手。你的任务：
1. 理解作战指令/情报报告，识别主意图（快速渡河/隐蔽渡河等）与任务分类（渡口选址/浮桥构筑/交通管制等）。
2. 抽取渡河所需数十项环境参数（水温、水深、流速、岸滩坡度、地质、敌情威胁等），只抽取文本中明确或可合理推断的内容，标注来源与置信度，严禁编造。
3. 结合知识库检索结果与图像识别要素，生成渡河工程保障方案。
【约束】所有输出必须符合给定 JSON Schema；不确定字段输出 unknown 并标记；方案必须通过规则引擎校验后才能作为正式输出。
【当前指令】{{指令文本}}
【知识库参考】{{检索结果}}
【图像要素】{{图像识别结果}}
【抽取参数表】{{上一轮抽取结果(重试时附带规则失败原因)}}
```

## 2. Agent B：路线规划助手（对应指标2）

### 2.1 输入 / 输出定义

| 项 | 内容 |
|----|------|
| 输入 | ① 自然语言机动/行动路线需求（含起终点、约束：隐蔽、避开障碍、时限）② 现场/侦察影像（可选） ③ 选定区域 |
| 输出 | 结构化 JSON：语义解析结果、坐标化后的路线要素、障碍物/威胁清单、推荐路线(GeoJSON)+备选路线、评估报告、多场景对比 |

### 2.2 Dify 工作流（Workflow + Agent 节点）编排序列

```
[开始-User Input] 接收: 自然语言需求 + 影像(可选) + 区域范围
   │
   ├─[Parameter Extractor] 路线需求语义解析 (起终点/途经点/约束条件/优先级)  ← JSON Schema
   │
   ├─[工具] 地理编码API (NL→坐标: 明确坐标→精确点; 地标/相对描述→推算范围)
   │        → 起终点坐标、途经点、约束多边形
   │
   ├─[Agent 节点] 距离/方位描述解析 → [工具] 距离计算与半径统计API
   │        → 实体距离、半径内要素统计(障碍/道路/地标)
   │
   ├─[工具] 影像障碍物识别API (路障/地雷/反坦克壕/伪装网/障碍物堆叠, 多目标+置信度)  ← 有影像时
   │        → 障碍物清单 + 分布图
   │
   ├─[知识检索] 地理环境知识库 RAG (路网/地志/通行性)
   │
   ├─[工具] 路网分析API (加载路网, 障碍物栅格化 → 阻断段标记)
   │
   ├─[Agent 节点] 路径规划编排 (A*/Dijkstra, 权重动态调整: 优先距离/安全/通行性)
   │        → 推荐路线 + 备选路线 (GeoJSON)
   │
   ├─[工具] 空间分析API (坡度/坡向/可视域/通视, 对候选路线做通行性校验)
   │
   ├─[LLM] 评估报告生成 (可行性与风险: 通过性/暴露风险/耗时/资源) 
   │
   ├─[工具] 多场景模拟API (不同兵力部署 → 生成多套评估报告)
   │
   ├─[Human Input] 人工确认节点 展示待确认项 (障碍物识别结果/路线选择/评估修正)
   │        ├─ 修正 → 标注数据回流(训练回路)
   │        └─ 通过
   └─[Output] 输出路线 GeoJSON + 评估报告 → 前端 planning 模块 / Cesium 标绘
```

### 2.3 外部工具清单

| 工具 | API | 指标对应 | 实现 |
|------|-----|---------|------|
| 地理编码 | `POST /gis/geocode` （NL→坐标/推算范围） | C-1 | Java（地名词典+GeoTools） |
| 距离计算与半径统计 | `POST /gis/spatial/range` | C-2 | Java（GeoTools/JTS） |
| 影像障碍物识别 | `POST /tools/image/obstacle-detect` | D-2/D-3/D-4 | Python（YOLO 微调，独立服务） |
| 路网加载与阻断分析 | `POST /gis/network/block` | A-7 | Java（JGraphT/GraphHopper） |
| 路径规划 | `POST /gis/network/route`（A*/Dijkstra + 动态权重） | 第四系统 | Java（GraphHopper/JGraphT） |
| 空间分析 | `POST /gis/analysis/terrain`（坡度/坡向/可视域/通视） | B-1.5 | Java（基于 DEM）；算法复杂时 Python(richdem) |
| 多场景模拟 | `POST /gis/scenario/run` | A-8 | Java |
| 标注回流 | `POST /tools/feedback/annotate` | A-9/D-5 | Java |

### 2.4 关键实现细节

**NL→标绘（对齐 C-1，本 agent 核心价值）**
- 地理编码工具内置：地名词典 + 逆地理编码；对"xx桥西北 2 公里"类相对描述，用参考地标坐标 + 方位/距离推算范围多边形。
- LLM 解析出坐标或描述后，统一输出 GeoJSON 要素（point/line/polygon），前端 Cesium 渲染，形成"自然语言 → 态势标绘"闭环。

**障碍物识别（对齐 D 节 5 类以上）**
- YOLOv11 微调 5 类：`路障/地雷/反坦克壕/伪装网/障碍物堆叠`，输出 `{class, bbox, confidence}`，多目标检测。
- 置信度 < 阈值的目标进人工确认列表；修正结果回流训练集，形成"识别→人工校验→再训练"回路（对齐 A-9/D-5）。
- 识别结果栅格化到路网 → 阻断段标记 → 路径规划避开（对齐 D-6）。

**路线规划（对齐第四系统）**
- 路网图加载（OSMnx/Pyrosm 或自建），障碍物与地形数据作为代价图层。
- A*/Dijkstra，代价权重可动态调整（`优先隐蔽/优先快速/优先安全`），对齐 A-6"动态调整分析权重"。
- 输出 `recommended` + `alternatives` 多路线，供多方案对比。

**多场景模拟（对齐 A-8）**
- 场景参数（兵力部署、威胁等级、时间窗）模板化，工具批量跑，产出多套评估报告；LLM 负责报告文本框架，数据来自真实计算。

### 2.5 提示词框架（骨架）


## 3. 共用基础服务与数据层（两个 agent 的底座）

> 技术栈策略：**工具/业务服务一律 Spring Boot (Java)**；Python 仅在深度视觉、栅格/DEM 算法等优势场景独立成微服务，供 Java 侧 HTTP 调用。各服务对 Dify 通过 OpenAPI 导入或 MCP 暴露。

| 服务 | 技术选型 | 语言 | 用途 |
|------|---------|------|------|
| API 网关/工具后端 | Spring Boot 3 (Java 17+) + springdoc-openapi | Java | 承载规则引擎、地理编码、路径规划、渡厂筛选、跨模态融合等工具 API；OpenAPI 导入 Dify 或包装为 MCP Server |
| 规则引擎 | Drools / Easy Rules | Java | 渡河硬约束校验（浮桥跨度↔水深等） |
| 空间数据库 | PostgreSQL + PostGIS | — | 路网、地志、障碍物、标绘要素 |
| 对象存储 | MinIO | — | 影像/街景/倾斜摄影原始文件 |
| 向量库 | Milvus / pgvector | — | 渡河知识库、地理环境知识库（嵌入由 Dify 完成） |
| 瓦片服务 | GeoServer 或 GeoTools 自研（TMS/WMS/WMTS） | Java | 影像/DEM 金字塔发布；也可接 GDAL 工具预生成 |
| 视觉/图像识别 | YOLOv11 / Qwen-VL 微调（FastAPI/独立 Python 服务） | Python | 水域要素识别 / 障碍物识别（Python 优势场景，独立部署） |

| 任务调度 | Spring Batch / Quartz（或 Redis Stream） | Java | 图像识别、切片等异步重活 |
| 地理编码 | 自研（地名词典）+ 逆地理编码（GeoTools） | Java | NL→坐标 |
| 跨模态融合 | 向量拼接/加权（可对接嵌入 API） | Java | 文本向量 + 图像特征融合 |

## 7. 落地前置条件与风险

- **数据**：先接 2-3 份真实样本（指令文本、现场图片、TIFF 影像），其余保持 mock 但字段对齐。
- **LLM 选型**：内网化场景优先 Qwen2.5-72B / DeepSeek 本地部署；多模态用 Qwen-VL/InternVL。
- **Dify 1.16 版本要点**：① 新版 Dify Agent 处于 Beta，官方建议仅开放给可信用户（含 Linux 沙箱 + Skills）；如不启用，则完全用 Workflow 节点实现，不依赖 Agent 应用。② 1.16 升级需核对 docker-compose 新增 `agent_backend`、`local_sandbox` 服务与 `DIFY_AGENT_SERVER_SECRET_KEY` 环境变量。③ 若用 OpenAI 新模型，API 类型默认已切到 Responses。
- **Dify 能力边界**：切片/瓦片服务、Cesium 渲染、模型训练不属于 Dify，均作为外部服务，Dify 只做编排。
- **主要风险**：图像识别准确率与标注数据不足 → 用人工校验回流 + 冷启动样例集缓解；地理编码对非结构化描述依赖地名词典质量 → 优先支持明确坐标与常见地标。
