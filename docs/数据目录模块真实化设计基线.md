# 数据目录模块真实化设计基线

> 目标：将前端全 mock 的 `src/views/catalog` 模块真实打通后端，接入真实数据。切片/服务发布不在本模块范围（由独立切片服务负责）。
> 制定时间：2026-08-20（经 grill-me 逐分支确认）

## 一、总体定位

数据目录 = **元数据登记系统 + 文件落地通道**，与 GIS 处理流水线解耦。

- 用户上传原始文件（TIF/DEM/影像/文档/三维等）→ 文件本体落 MinIO → 同时在 `data_catalog` 登记一条元数据。
- 目录**不触发切片**，只登记“某数据已有 / 格式 X / 位置 Y / 范围 Z / 状态 W”。切片与服务发布由独立切片服务消费目录元数据后自行处理。

## 三、后端架构（geo-llm-service 模块）

与 `/system/vector` 同模块，复用 Spring Boot + MyBatis/MP 体系。

### 3.1 数据模型

**`data_catalog`（主表，公共字段）**

> **对齐结论**：去掉独立的 `type` 字段。`data_catalog` 只存 `category_id`（指向 `data_category` 的**叶子节点**），所谓"大类/type"（遥感影像/DEM/…）由分类树祖先链推导。前端 `typeOptions`（大类下拉）从 `category/tree` 的一级节点动态生成，不再独立维护 type。

| 字段                    | 说明                                                         |
| ----------------------- | ------------------------------------------------------------ |
| id                      | 主键                                                         |
| name                    | 数据名称                                                     |
| category_id             | 分类叶子节点 id/code（关联 data_category）；大类由祖先链推导 |
| format                  | 文件格式（tif/img/egc/...）                                  |
| crs                     | 坐标系                                                       |
| bbox                    | 空间范围（WKT 或 lon/lat 四元组）                            |
| object_key              | MinIO 对象 key                                               |
| url                     | 访问 URL                                                     |
| thumbnail               | 缩略图 key/url                                               |
| size                    | 文件大小                                                     |
| source                  | 数据来源                                                     |
| status                  | 状态（草稿/已发布/...）                                      |
| extend_json             | JSONB，存类型差异字段（分辨率/波段/高程范围/LOD 等）         |
| create_by / create_time | 登记人/时间                                                  |

**`data_category`（轻量字典表）**

| 字段   | 说明                                    |
| ------ | --------------------------------------- |
| id     | 主键                                    |
| code   | 分类 code（如 `img`、`imq-optical`）    |
| parent | 父级 code/id（一级为 null，支持多级树） |
| name   | 分类显示名                              |

**明确不进表的字段**：`agentBinding`、`scenarioTags`（本期不接真实过滤，前端下拉保留但不过滤真实数据）。

### 3.2 文件存储（local / minio 可配置，方案 B1）

**现状**：`geo-llm-system` 模块已有 `StorageTypeEnum{LOCAL, OSS}` + `StorageServiceImpl.load()` 的二选一能力（基于 `x-file-storage`），但 `geo-llm-service` 模块目前只有 `vector` 包、完全没有存储抽象，矢量上传是 `MultipartFile` 直接落本地临时目录，没有 local/minio 开关。因此数据目录的"二选一"需在 `geo-llm-service` 内从零建设，**不跨模块依赖 system 的 `StorageService`**（也符合"目录不依赖 `/system/file` 通用桶"的既定原则）。

**方案 B1（已确认）**：数据目录在 `geo-llm-service` 内自建轻量存储层，由 `application.yml` 单开关切换：

- 新增 `CatalogStorageHandler` 接口（presign / upload / delete / getDownloadUrl 等），下挂两个实现：
  - `LocalCatalogStorageHandler`：文件落本地磁盘（路径由 `geollm.catalog.storage.local.path` 指定）。
  - `MinioCatalogStorageHandler`：走 AWS SDK 2.x S3 客户端，落 MinIO `geollm` bucket（endpoint/key/secret 取自 `geollm.minio.*`）。
- `application.yml` 配置 `geollm.catalog.storage.type=local|minio`，Spring 按 type 注入对应 Handler 实现（@ConditionalOnProperty 或工厂路由）。
- 上传主流程（presigned 直传）保持不变，只是 presign 能力由 `MinioCatalogStorageHandler` 提供；local 模式下退化为服务端中转上传（本地存储无 presigned 概念）。

**核心约束**：

- 行业主流大文件走 **presigned URL 直传 MinIO**；local 模式仅用于本地开发/离线演示，小文件中转即可。
- MinIO 用预留 `geollm` bucket（`geollm.minio.*` 配置），不依赖 `/system/file` 通用桶。
- 上传流程：前端 → `POST /catalog/presign` 取临时上传 URL（minio 模式）→ 前端直传 → `POST /catalog/register` 回调登记元数据。
- **现状缺口**：需补 presigned URL 生成能力（AWS SDK 2.x `PutObjectPresignRequest` / `UploadPartPresignRequest`）；MinIO 当前 `sys_storage` 无 OSS 记录未真通，目录模块自持 `geollm.minio.*` 配置。

### 3.3 后端接口集合

> **接口前缀对齐结论**：数据目录接口统一使用 **`/service/catalog/**`** 前缀（保留原定方案）。因 `geo-llm-service`现有矢量是`/system/vector`，二者前缀不同，**需在后端 Swagger 分组中新增 `service`组的匹配规则以覆盖`/service/catalog/**`**（与现有 `/system/vector/**` 并存），避免目录接口落入错误分组。

| 方法 + 路径                              | 用途                                                                   |
| ---------------------------------------- | ---------------------------------------------------------------------- |
| `GET /service/catalog/page`              | 分页 + 按 category_id（叶节点）/大类（祖先）/keyword 筛选              |
| `POST /service/catalog/presign`          | 生成 MinIO 直传 presigned URL（分片或单 PUT）                          |
| `POST /service/catalog/register`         | 上传完成回调，写 `data_catalog` 一条元数据（需服务端 headObject 校验） |
| `POST /service/catalog/{id}/publish`     | 改 status（仅目录状态，不触发切片）                                    |
| `DELETE /service/catalog/{id}`           | 删元数据 + 删 MinIO 对象（先删对象，成功后再删元数据）                 |
| `GET /service/catalog/{id}/download-url` | 返回 presigned GET URL（下载）                                         |

### 3.4 分类字典管理（`data_category` 的维护入口）

**问题背景**：左侧分类树接入真实后端后，必须有地方维护 `data_category`（否则分类只能手填 SQL）。后端已有通用系统字典 `sys_dict`/`sys_dict_item`（`/system/dict`），但其 `DictItemDO` 是扁平键值（label/value/dictId），**无 parent 父子字段，不支持多级树**，无法承载"遥感影像→img/imq-optical/imq-sar"这类多级分类。因此 `data_category` **独立建表 + 独立管理**，不复用 `sys_dict`。

**后端需补充的管理接口**（在 `geo-llm-service` 新建 `DataCategoryController`）：

| 方法 + 路径                             | 用途                                                           |
| --------------------------------------- | -------------------------------------------------------------- |
| `GET /service/catalog/category/tree`    | 返回完整分类树（含每类在 `data_catalog` 的计数），供左侧树渲染 |
| `POST /service/catalog/category`        | 新增分类节点（指定 code/parent/name）                          |
| `PUT /service/catalog/category/{id}`    | 修改分类节点                                                   |
| `DELETE /service/catalog/category/{id}` | 删除分类节点（有子节点或已关联数据时报错拦截）                 |

> 注：分类树**一级节点即"大类"**（遥感影像/数字高程/…，对应原 mock 的 `type`），叶子节点为具体子类。分类树 + 每类计数统一由 `GET /service/catalog/category/tree` 返回；`GET /service/catalog/page` 只管列表，不重复返回树，避免前端两次请求与职责重叠。

**前端需补充的管理页/组件**：分类树不仅是展示，还要可维护。在"数据目录"模块内提供分类管理入口（避免和通用系统字典页混用）：

- `views/catalog/modules/catalog-category-manage.vue`：分类树管理弹窗（新增/编辑/删除节点、拖拽或选父级），调用上述 4 个管理接口。
- 列表主页 `catalog-category-tree.vue` 增加"管理分类"入口按钮，打开该弹窗。
- 前端 `typeOptions`（大类下拉）与左侧分类树均从 `category/tree` 生成，不再维护独立的 type 枚举。

### 3.5 上传安全与数据一致性

- **register 服务端校验**：presigned 直传后，前端调 `register` 时后端需按 `object_key` 调 MinIO `headObject`，确认对象真实存在并校验 `size`/`etag`/`contentType` 与 presign 登记一致，通过才落库，防止伪造/异常登记。
- **presign 类型约束**：`POST /service/catalog/presign` 入参带 `fileName`/`categoryId`，服务端校验扩展名与分类允许类型，并在签名的 URL 上附带 `Content-Type` 与大小上限约束。
- **删除顺序**：`DELETE /service/catalog/{id}` 先删 MinIO 对象、成功后再删 `data_catalog` 元数据；对象删除失败则中止并返回错误，避免残留孤儿对象或死链。

## 四、前端改造（geo-llm-ui）

### 4.1 现状问题

当前 `src/views/catalog/index.vue` 是一个 **1500+ 行的单文件巨页**，把列表、左侧分类树、上传弹窗、发布/下载/删除操作、详情抽屉、分析弹窗全部耦合在一起，且全部为前端 mock。真实化时应按职责拆页/拆组件，而不是在一个文件里继续堆。

### 4.2 页面与组件划分（推荐）

路由仍保持单一入口 `/catalog`（菜单"数据目录"），但内部按"列表主页面 + 弹层/抽屉"组织，不拆成多个路由页（避免菜单膨胀，也符合现有 elegant-router 单 route 结构）：

| 文件                                                | 职责                                                | 真实化要点                                                                                                                        |
| --------------------------------------------------- | --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `views/catalog/index.vue`                           | **列表主页**：左分类树 + 顶部筛选 + 数据表格 + 分页 | 接 `GET /service/catalog/page`；分类树接真实 `data_category`；发布/删除/下载接真实接口                                            |
| `views/catalog/modules/catalog-category-tree.vue`   | 左侧分类树组件                                      | 由后端 `GET /service/catalog/category/tree` 返回树渲染（含每类计数），替换硬编码 `catalogCategories`；含"管理分类"入口            |
| `views/catalog/modules/catalog-category-manage.vue` | 分类树管理弹窗                                      | 调 `category` CRUD 接口，新增/编辑/删除节点、选父级                                                                               |
| `views/catalog/modules/catalog-upload-modal.vue`    | 上传弹窗                                            | 选分类 → 调 `POST /service/catalog/presign` 取 URL（带类型/大小约束）→ 前端直传 MinIO → `POST /service/catalog/register` 回调登记 |
| `views/catalog/modules/catalog-detail-drawer.vue`   | 详情抽屉                                            | 展示单条元数据（bbox/坐标系/分类祖先链/extend_json 等）                                                                           |
| `views/catalog/modules/catalog-analysis-modal.vue`  | 分析弹窗                                            | **保留 mock 不动**（`getMockGeoJSON` 假矢量），标注"待接分析服务"                                                                 |
| `service/api/catalog.ts`                            | 接口封装层（新建）                                  | 封装目录 6 个接口 + 分类 4 个接口，共 10 个                                                                                       |

**不新增独立路由页**的理由：列表主页 + 弹窗/抽屉即可覆盖全部操作，拆多路由反而增加 tab 切换成本；分类树/上传/详情/分析均为"在列表上下文内"的子交互，适合用 modal/drawer 而非页面。

### 4.3 其他改造点

- 新建 `src/service/api/catalog.ts` 封装目录 6 个接口 + 分类 4 个接口。
- 删除对独立 `type` 枚举的依赖：`typeOptions`（大类下拉）与分类树均从 `category/tree` 生成；`CatalogItem.type` 相关展示改由分类祖先链推导。
- **分析弹窗保持 mock 不动**：`getMockGeoJSON` 假矢量、要素提取/目标检测演示逻辑原样保留，标注"待接分析服务"。
- `agentBinding` / `scenarioTags` 两个下拉：本期保留 UI 但不过滤真实数据（或隐藏）。

## 五、实施依赖与风险

1. **MinIO 未真通**：`sys_storage` 表无 OSS 类型 MinIO 记录，目录模块需自持 `geollm.minio.*` 客户端配置。
2. **presign 能力缺失**：需给目录模块的 `MinioCatalogStorageHandler` 补 presigned URL 生成方法（AWS SDK 2.x `PutObjectPresignRequest` / `UploadPartPresignRequest`），含 `headObject` 校验。
3. **Swagger 分组**：`service` 组当前只匹配 `/system/vector/**`，需新增匹配规则覆盖 `/service/catalog/**`。
4. **矢量模块现状参考**：`geo-llm-service` 现有矢量上传是本地临时目录写法（过渡实现），目录模块应做“正确版本”走 MinIO，不复制该写法。

## 六、建议实施顺序

1. **后端优先**：在 `geo-llm-service` 建 `data_category` / `data_catalog` 表与 entity/mapper；实现 `CatalogStorageHandler`（local/minio 二实现 + presign + headObject 校验）；写 `DataCatalogController` + `DataCategoryController`（接口闭环）；调整 Swagger `service` 组匹配。
2. **前端跟进**：建 `catalog.ts` + 拆 `index.vue` 组件接真实接口，分类树/大类下拉走 `category/tree`，分析弹窗保留 mock。
